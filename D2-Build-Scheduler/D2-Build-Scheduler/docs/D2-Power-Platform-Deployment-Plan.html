This plan moves the working browser-based scheduler onto Dataverse, with a desktop app for the office and PMs, an offline-capable mobile app for crew leads signing off in the field, and Power BI for ownership. The scheduling logic runs in Power Automate — no C# — with one structural trick that makes double-booking impossible without writing code.

01The decision

Build custom tables in Dataverse rather than adopting Dynamics 365 Field Service. Field Service is built around work orders: short, dispatchable jobs with a technician, a time window, and a service call. A D2 pool is the opposite shape — 46 sub-phases in a fixed sequence, stretched across three to four months, where the constraint is which crew is free for a two-day block and has the qualifying trade. Field Service's Schedule Board would have to be bent hard to model that, and it lists near $95 per user per month against roughly $20 for Power Apps Premium.

What Field Service gives you for free — a Gantt-style Schedule Board — is the one real gap in this plan. Section 06 addresses it honestly.

02How a booking gets rejected

This is the mechanism the whole low-code decision rests on, so it goes first.

The rule that matters is: a field crew can be on exactly one pool per day. With a C# plug-in you would enforce this inside the database transaction. Without one, a Power Automate flow reading availability and then writing an assignment has a gap between the check and the write — two PMs scheduling at the same moment can both pass the check and both write.

The fix is structural rather than procedural. A Crew Day table holds one row per crew per booked day, with a Dataverse alternate key on Crew + Date. Dataverse enforces that uniqueness at the database level. The second write doesn't get validated and rejected by logic you wrote — it fails on the key, the way a duplicate primary key fails. The flow catches the error and moves to the next available day.

Two consequences worth stating up front. First, Crew Day rows are only written for real field crews — Main Office, Subcontractor, and Unassigned are capacity-exempt and would collide with themselves on every job. Second, the flow is still not atomic: a mid-run failure can leave orphaned Crew Day rows. Every row created in a run is stamped with a run ID so a compensating step in the error branch can delete them.

Two Dataverse behaviours to design around

Scheduled Finish cannot be a calculated column. Calculated columns can't skip Sundays, holidays, and weather days. The flow computes and writes it.

Rollup columns refresh on a schedule, not instantly — typically hourly. Use a rollup for checklist completion in Power BI, but calculate the on-screen percentage in the app with a live count, or crews will tick a box and see no change.

04The scheduling flow

One cloud flow, Auto-Schedule Job, triggered by a button on the Job form. The naive build issues a Dataverse query per crew per sub-phase and takes fifteen minutes. This one reads everything once and does the arithmetic in memory:

  1. Three reads, up front. Future Crew Days, all Crew Trades, the Work Calendar — into array variables.
  2. List the job's sub-phases in sequence, excluding those marked Not Applicable.
  3. Loop, sequentially — concurrency must be off, because each sub-phase starts after the one before it ends.
    • Locked → keep its dates, advance the cursor past it.
    • Assigned to Main Office / Subcontractor / Unassigned → set the crew, write no Crew Days, advance.
    • Otherwise → filter the in-memory trade list to qualified crews, walk forward from the cursor to the first working-day block of the right length where one of them has no Crew Day, and take the crew with the lightest load.
  4. Write the sub-phase and its Crew Day rows; append them to the in-memory array so later iterations see them.
  5. Stamp the job's Scheduled Finish.

Accept this trade-off knowingly

Ninety seconds of spinner is the price of no C#. It is fine for a button a PM presses when a pool is sold or a phase slips. It would not be fine as a real-time recalculation on every date edit — so don't build one. If the wait becomes intolerable, the same logic ports to a Dataverse Custom API and drops to about two seconds; the data model doesn't change.

Offline sync, honestly

Power Apps offline resolves conflicts last-write-wins. That is dangerous on a shared record — but crew leads only ever write sign-off and task completion. Lock them out of crew and date columns with a column-security profile and the failure mode disappears.

06The Gantt gap

Model-driven apps have no native Gantt, and without custom code you cannot build the board that exists in the browser tool today. Three options, none perfect:

08Environments and release

Three environments — D2 Dev, D2 Test, D2 Prod — with everything in one solution, D2BuildScheduler, publisher prefix d2. Ship with Power Platform Pipelines, which is built into the maker portal and needs no Azure DevOps. Dev exports unmanaged; Test and Prod import managed, so nobody can hand-edit production.

09Data migration

About 450 template rows, loaded in dependency order: Trades → Crews → Crew Members → Crew Trades → Phase Templates → Sub-Phase Templates → Task Templates. Sources are the existing MASTER TO COPY FROM D2 Gunite Build Phases.xlsx and D2 Pools Crews.pdf. Excel import in the maker portal handles this in an afternoon.

Five data gaps to close before migration — this is the real critical path

None of these are technical. All of them will be baked into production if they go across unresolved.

  1. Four crews have no size or member list — George, Armondo, STL Shotcrete, Brothers.
  2. Ten trades map to no sub-phase: Retaining Walls, Veneer/Stone, CMU, Brick/Masonry, Landscaping, Pavers, Forms, Water Line Install, Material Runs, and plain Grading. George Crew is currently scheduled zero days of work as a direct result.
  3. Finish Grade on Saul and Guillermo is an inference, drawn from Cirilo being the only crew explicitly excluded from it. Not stated on the crew list.
  4. Eleven sub-phases sit in Unassigned — the field supervision and QC items. They need an owner, or a PM crew needs to exist.
  5. All 46 durations are the 2-day placeholder. Fine for building the system; not fine for promising a customer a finish date.

The browser tool is the test oracle

It already enforces the same rules — sequence, trade matching, one crew per day, Mon–Sat — and its output has been verified across twelve concurrent jobs. Feed both systems the same three pools in week 7. Any divergence is a bug in one of them, and you know which rules to check.

13Open decisions

  1. Should a PM crew exist? Eleven sub-phases are field supervision and QC, currently parked in Unassigned. A fourth capacity-exempt bucket would clear them in one pass.
  2. Where do the ten unmapped trades belong? Most likely inside existing sub-phases — retaining walls and veneer under 5.6 Deck Placement, forms under 2.2 Steel Installation — or the template is missing sub-phases D2's process actually has.
  3. Per-app or Premium for crew leads? Roughly $150 a month, contingent on offline support.
  4. Who builds it? The plan assumes an internal low-code maker. It is also written tightly enough to hand to a Microsoft partner as a scope of work.
